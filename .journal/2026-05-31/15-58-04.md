## Session Update

*Author: Claude (Opus 4.8) — Tex.* On-host verification of Phase 2 `vm_setup`.
Jonny ran it against a real Hyper-V host; we chased the failures the live run
surfaced and landed on WinRM for provisioning. Ended at commit `9eff408`
(also fast-forwarded onto `main`). 148 tests green throughout.

### The headline finding (don't relearn this)

**Hyper-V *write* cmdlets (New-VM/New-VHD/Set-VM*) can't run reliably over a
DCOM-protocol CIM session; they need WinRM.** Read-only enumeration (our VM
listing via `System.Management`, `Get-VM`) is fine over DCOM. The DCOM CIM
session (commit `b6e252a`) was chosen to dodge WinRM setup, but it
half-created VMs then RPC-timed-out on the next cmdlet — intermittent enough to
look like it worked once. Symptom progression: module-autoload error → created
VM but stalled on New-VHD → `VirtualizationException` (the Hyper-V module's own
type — tells you the cmdlet ran locally and its CIM call to the host failed).

### Fixes, in order (all in HyperVHost.cs)

1. **Pipe deadlock.** `RunOnHost` read stdout to end *then* stderr — classic
   .NET deadlock when the child floods the unread pipe. PowerShell error spew on
   stderr triggered it; looked like a UI stall (it wasn't the UI thread — the
   whole path is `Task.Run` + awaited; the agent loop was just hung on the
   wedged process). Fix: drain both concurrently (`ReadToEndAsync` ×2 before
   `WaitForExit`).
2. **Surface the VM id on partial failure.** `CreateScript` now prints
   `$vm.Id.Guid` *immediately after* New-VM, before any config cmdlet.
   `RunOnHost` returns `(stdout, stderr, exitCode)` instead of throwing, so the
   create path can report "VM created ({id}) but configuration failed: … — alter
   or delete it" rather than orphaning a VM and reporting total failure. Test:
   `Create_PrintsIdBeforeConfig…` asserts the id precedes New-VHD/Set-VMProcessor.
3. **Back to WinRM (`9eff408`).** `RemoteWrapper` runs the script on the host via
   `Invoke-Command -Credential -Authentication Negotiate` — cmdlets execute where
   Hyper-V lives. Dropped the DCOM CIM session and the local `Import-Module
   Hyper-V` (that was a DCOM-CDXML-autoload workaround; locally we may not even
   have the module).

### The trust/elevation wall (why we don't self-configure)

WinRM to an IP/workgroup host with NTLM needs the host in the *client's*
TrustedHosts + the WinRM service running — and **both require elevation Jabsco
doesn't have** ("needs to run from an elevated process"). First attempt put
`Start-Service WinRM` + `Set-Item …TrustedHosts -Concatenate` in the wrapper; it
threw. So we **don't self-configure**: `ProvisioningFailure` detects a
WinRM/TrustedHosts error in stderr and surfaces the one-time elevated command:
`Set-Service WinRM -StartupType Automatic; Start-Service WinRM; Set-Item
WSMan:\localhost\Client\TrustedHosts -Value '<host>' -Concatenate -Force` (+
`Enable-PSRemoting -Force` on the host). Symmetric with the host-side hint.
README documents both ends. Jonny ran it once, and create worked end-to-end.

### Red herrings worth remembering

- "Secure Boot/Checkpoint didn't apply" → Jonny was **looking at the wrong VM**.
  It worked. (Parse and script-gen both handle `false` correctly: `Bool` returns
  `GetBoolean()`; `is { }` skips only null.) Always confirm you're inspecting the
  right object before debugging the code.
- The local **WinRM service** was Manual/stopped — likely the "Windows
  Management System off/Manual" Jonny saw (real name: Windows Remote Management).

### ⚠️ Working-tree truncation event (not us)

After the commit, `git status` showed 32 tracked files at **0 bytes** —
HyperVHost.cs had compiled minutes earlier, so this was external truncation, not
our edits. HEAD (`9eff408`) had full content; recovered with `git restore .`,
clean after. Lesson: a wall of "modified" files that are all 0 bytes = working-
tree corruption, not real changes. **Do not commit over them** — restore from
HEAD. Checked reflog + `git cat-file -s HEAD:<file>` to confirm HEAD was intact
before restoring.
