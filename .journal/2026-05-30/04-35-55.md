### Two decisions I put to Jonny (AskUserQuestion)

- **Running-VM guard live-safe set:** checkpoints + guest services + enhanced session are
  live-safe; everything else (memory, cpu, disk, iso, tpm, secure boot, nic, generation) is
  hardware-class → `VmSpec.RequiresStoppedVm`. Enforced in `ConnectionController.RunVmSetupAsync`
  against the **cached** VM state (`_cachedVms`, which DescribeAsync keeps fresh each step). No
  auto-stop — throws InvalidOperationException, the loop returns it as a tool result.
- **Provisioning impl: PowerShell, not raw WMI.** I pushed back on the spec's
  `DefineSystem`/`ModifySystemSettings` line — full provisioning (VHD create+attach, ISO, TPM
  key protector, NIC+switch) in raw WMI is ~300-400 lines of untestable embedded-instance
  rituals, and DCOM write-auth is worse than the read-only listing. Hyper-V cmdlets map 1:1
  and are far more maintainable. Jonny agreed. Connection stays WMI/VMConnect; only create/alter
  uses PowerShell.

### The PowerShell design (the nice part)

`HyperVHost.CreateScript(spec)` / `AlterScript(vmId, spec)` are **pure, public static, and
unit-tested** — they generate the Hyper-V cmdlets, emitting a cmdlet *only* for each provided
field (so partial alter falls out naturally). Create → `New-VM ... -NoVHD` then common settings
then `$vm.Id.Guid`; alter → `Get-VM -Id` then only what changed. Single quotes escaped via
doubling. The untestable integration layer is just `RunOnHost`: spawns `powershell.exe -Command -`,
passes host/user/pass/script through the **environment** (no secret on the cmdline), and the
script runs inside `Invoke-Command -ComputerName ... -Credential ... -ScriptBlock $sb` so cmdlets
execute locally on the host. Returns stdout; create parses the last line as the new GUID.

This split — pure script-builder + thin process runner — is the pattern to reuse for any
"shell out to do X on the host" work. It made provisioning testable on Linux.

### 🖖 Needs on-host verification (Windows + WinRM)

Requires `Enable-PSRemoting` on the host (aligns with the access-denied hint we already show).
Open Qs for the real run, flagged in the todo:
- Default VHDX path uses `(Get-VMHost).VirtualHardDiskPath` + `$vm.Name.vhdx` — verify it's writable.
- **Enhanced session is host-wide** (`Set-VMHost -EnableEnhancedSessionMode`), not per-VM — there's
  no clean per-VM cmdlet. May want to revisit if per-VM transport matters.
- No boot-order set after attaching VHD/ISO — a fresh gen2 VM may not boot the ISO without it.
- TPM uses `Set-VMKeyProtector -NewLocalKeyProtector` (local, not HGS) before `Enable-VMTPM`.
