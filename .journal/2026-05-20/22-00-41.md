## Session Update

Continuation of the first Jabsco session. Three things happened after the initial scaffold commit.

**Build fixes (two minor Avalonia 12 issues):**
- `TextBox.Watermark` → `PlaceholderText` in PromptComposerView
- `StackPanel` doesn't have `Padding` in Avalonia 12 → wrapped in `Border`
- `Tmds.DBus.Protocol` version conflict: Core had 0.93.0, Avalonia.FreeDesktop needs 0.92.0. Downgraded Core. Lesson: Avalonia.FreeDesktop pins Tmds.DBus — always match it.

**Full UI redesign:**

Jonny wanted to move away from the 3-pane layout toward something that feels native to Windows. The new design:
- Tab bar: persistent "Connections" tab + one tab per active session (hostname + close ×)
- Connections tab: centered card with recent connections + new session form
- Session tab: full-area RDP framebuffer, translucent chat overlay floating right (togglable), bottom toolbar

Key design details Jonny specified:
- Windows-native aesthetic (Segoe UI, white/gray, #0078D4 — like Notepad)
- Chat overlay is semi-translucent (80% opaque white panel), individual bubbles fully opaque, like "clouds passing over"
- Stop button in the chat to cancel agent actions
- Cursor trails (fading dots), click rings (expanding circles), target boxes (dashed rect) rendered over the framebuffer

The cs-coder agent wrote all of it. One notable bug it produced: `IsVisible` bindings on child views in `MainWindow.axaml` were resolving against each view's own DataContext type (`ConnectionPanelViewModel`, `SessionViewModel`) instead of `MainWindowViewModel`. Fix was to wrap each view in a `Panel` so the `IsVisible` binding stays bound to the window's DataContext context, and only the child view gets the specialized DataContext. Classic Avalonia compiled-binding gotcha — the compiler infers DataContext type from the DataContext property binding, so a sibling `IsVisible` on the same element uses the *new* type, not the parent's.

**Cross-compilation:**

Jonny asked for a `mise.toml` with tasks. .NET 10 cross-compiles cleanly to win-x64 from Linux. Verified: `Jabsco.Ui.exe` comes out as PE32+ GUI subsystem, CLI/Daemon as console subsystem. Native DLLs (SkiaSharp, SQLite) end up alongside the exe — can't be embedded since they're native code. That's expected and fine.

Tasks:
- `mise run publish:win` → publish/win-x64/
- `mise run publish:linux` → publish/linux-x64/
- `mise run publish:all` → both (mise runs depends in parallel)

Had to `mise trust` the config before it would parse. Noted for next session.
