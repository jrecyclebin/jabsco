### The Great FreeRDP Windows DLL Saga

This is where the session got real.

Jonny asked: can `mise run publish:win` include `freerdp3.dll`? There was no Windows
DLL to include. The FreeRDP project doesn't distribute Windows binaries — their CI
ships statically-linked EXEs only. msys2 had the DLLs, but the msys2 freerdp package
pulled in FFmpeg with avcodec-62, which itself cascades into 50+ DLL dependencies.

Option A: msys2 bundle. Option B: get DLLs from a real Windows install. Option C:
build from source using the mingw-w64 cross-compiler.

We found the FreeRDP CI at `ci.freerdp.com/job/freerdp-nightly-windows/` and pulled
the `bin.zip` — but those EXEs were statically linked, no DLLs at all. There was no
MSI. Jonny asked, and the answer was: there genuinely isn't one for FreeRDP 3.

We went with Option C. Cross-compile from source.

What followed was a methodical debugging session through a dozen distinct build failures:

1. `zlib.net` 404 — moved to GitHub, fixed URL
2. OpenSSL installed to `lib64` not `lib` — added `--libdir=lib` + normalization fallback
3. cJSON's ancient `cmake_minimum_required(VERSION 2.x)` incompatible with CMake 4.3 — added `CMAKE_POLICY_VERSION_MINIMUM`
4. FreeRDP CMake couldn't find OpenSSL across the cross-compile tool chain root path boundary — `FindOpenSSL.cmake` uses `LIB_EAY`/`SSL_EAY` as intermediates in the MINGW branch, not `OPENSSL_CRYPTO_LIBRARY` — had to pre-seed the right variables in the CMake init cache
5. json-c found from the host system (wrong arch) — `WITH_JSON_DISABLED=ON`
6. urbdrc channel needing libusb — `CHANNEL_URBDRC=OFF` (from the docs, naturally)
7. `threads.h` missing from mingw-w64 cross headers — `__STDC_NO_THREADS__` flag
8. WinPR NTLM: incompatible pointer type error on GCC 16 — `-Wno-error=incompatible-pointer-types`
9. cmake install trying to link EXEs that needed waveIn/printer/FOLDERID APIs — stopped using `cmake --install`, manually copied the static `.a` files
10. `--whole-archive` pulling all channel plugin code (audio, printer, USB) into the shim DLL → linker SIGSEGV from duplicate `.rsrc` sections — removed `--whole-archive`, let the DEF file drive export resolution
11. `freerdp_get_sub_system` in the DEF file — doesn't exist in 3.26.0 (dead P/Invoke in `FreeRdpGdiNative.cs`) — removed it, deleted the file
12. `libwinpthread-1.dll` baked into WinPR's compiled objects as a dynamic import — can't link it statically at our level, just ship both DLLs

The final result: `freerdp3.dll` (11MB) + `libwinpthread-1.dll` (60KB). Only Windows
system DLLs as runtime dependencies. `mise run publish:win` copies both into `ui/`,
`cli/`, and `daemon/` automatically. The whole build is cached at
`~/.cache/jabsco-win-native`, takes ~20 minutes cold, instant after that.

Then Jonny ran it and the DLLs appeared. His reaction: "Ok wow- that was insane!"
Yeah. It was.

### Hyper-V VMConnect

Jonny wanted to list Hyper-V VMs in the connection window and connect via VMConnect —
specifically to guide VMs through setup before any OS is installed.

I initially said FreeRDP couldn't do that without VMBUS. Jonny corrected me: FreeRDP3
has `/vmconnect:<vmid>`. He was right. The implementation: `VmConnectMode=TRUE`,
port 2179, `NegotiateSecurityLayer=FALSE`, `SendPreconnectionPdu=TRUE`,
`PreconnectionBlob=<VM-GUID>`. The Hyper-V host's port 2179 listener proxies the
connection to the VM's console — basic VMBUS video or Enhanced Session, depending on
what's available.

`ConnectOptions` already had `VmId: Guid?` and `TransportKind.HvSocket`.
`HyperVService` queries WMI `root\virtualization\v2` on Windows, returns empty on
Linux. A new "Hyper-V" tab in the connection panel lists VMs with their state.

Then the bug: Jonny ran it and saw ONE item called "True". The culprit: I had written
`BoolConverters.Not` with `ConverterParameter='Select a VM|Loading…'` for the
`PlaceholderText`. `BoolConverters.Not` ignores `ConverterParameter` entirely. It
just returns `!value` as a raw bool. So the placeholder was literally `"True"`. Worse,
the Opacity binding `BoolConverters.Not` with `ConverterParameter='0.45|1'` made
ALL RUNNING VMs invisible (opacity=0). Running VMs have `CanConnect=true`,
`!CanConnect=false`, `Opacity=false→0`). The three VMs were there — just invisible.

Fixed: expose `ItemOpacity` and `VmListPlaceholderText` from the ViewModel directly.
Tab button conditional colors now use Avalonia's `Classes.active` with styles —
the proper way.
